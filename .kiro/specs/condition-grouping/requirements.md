# Requirements Document

## Introduction

Condition grouping is Spec 2 of the Research Gap Index. It reads the study table already produced by Spec 1 (`pipeline/processed/studies.csv`, with `pipeline/processed/sites.csv` for the recall check) and assigns each study to zero or more CDC PLACES disease measures. It does not re-fetch study data. The MVP diseases are CASTHMA ("Asthma"), HIGHCHOL ("High cholesterol") and DIABETES ("Diabetes"). BPHIGH and DEPRESSION must be addable later by editing the rules file only.

The team-approved `burden_test/inclusion_rules.md` is the source of truth for which studies count. A study counts for a disease only if its participants match what the PLACES measure counts (adults 18+ ever told they have the condition). Unclear matches are marked questionable and reported separately, never silently counted.

The feature writes three files, all committed to git:

- `pipeline/processed/study_diseases.csv`, exactly as defined in the data contract (`.kiro/steering/data-contract.md`).
- `pipeline/processed/recall_check.json`, comparing our included Massachusetts study counts with ClinicalTrials.gov's own condition search counts.
- `burden_test/precision_sample.csv`, 20 seeded-random included studies per disease for hand-checking by the bio teammate.

Before `pipeline/mapping/rules.py` is written, a one-off Term_Audit (Requirement 14) lists the most frequent disease-related values in `studies.csv` and is saved as `.kiro/specs/condition-grouping/term_audit.md`. The Term_Audit is a development artifact and is not part of the pipeline run.

The entry point is `python -m pipeline.mapping`. The feature follows the same conventions as Spec 1: Python 3.11+, deterministic UTF-8 CSV output, atomic writes, errors to stderr with a non-zero exit code, no contact data, and network access limited to `clinicaltrials.gov` and `data.cdc.gov`.

### Input facts (from the current `studies.csv`)

- Header: `nctId, briefTitle, overallStatus, studyType, phases, healthyVolunteers, minimumAge, maximumAge, stdAges, conditions, interventionTypes, interventionNames, meshTerms, meshIds, ancestorTerms, ancestorIds, lastUpdatePostDate, source_url`. List columns (`conditions`, `meshTerms`, `ancestorTerms` and others) are JSON array strings.
- 16,079 rows. `overallStatus` values: RECRUITING, NOT_YET_RECRUITING, ACTIVE_NOT_RECRUITING, COMPLETED.
- `healthyVolunteers` values: `true`, `false`, or empty.
- `maximumAge` is empty (no upper limit) or `<integer> <unit>`, where unit is one of Year, Years, Month, Months, Week, Weeks, Day, Days, Hour, Hours, Minute, Minutes.
- `sites.csv` columns: `nctId, facility, city, state, zip, latitude, longitude, siteStatus, location_quality`. Massachusetts sites have `state` = "Massachusetts".

### Open Items and Assumptions

1. **Ancestor terms are study-level.** `ancestorTerms` is one list per study and is not linked to a specific MeSH term. A gestational diabetes study carries the ancestor "Diabetes Mellitus", and a diabetic retinopathy study may carry it too. Requirement 4 therefore lets an exclude match in `conditions` or `meshTerms` override an ancestor-only include, and Requirement 2 lets each disease set whether an ancestor-only match is included or questionable. The initial settings (Requirement 2 criterion 8) are CASTHMA = `included`, HIGHCHOL = `questionable` and DIABETES = `questionable`, pending confirmation by the bio teammate. DIABETES is questionable because inclusion_rules.md counts diabetic complications only when diabetes is a listed condition.
2. **"No matching patient condition" (healthy volunteers).** Interpreted as: the study has no include-term match in `conditions` or `meshTerms` for that disease on a value that is not a Masked_Value (only ancestor, questionable or exclude matches, or include matches on values that also match an Exclude_Term or Questionable_Term, per Open Item 15). A study with `healthyVolunteers = true` that also lists a matching patient condition (for example, an asthma study with healthy controls) is included.
3. **ASCVD-only for HIGHCHOL.** ASCVD and myocardial infarction terms are configured as HIGHCHOL exclude terms with reason `ascvd_only`. Studies matching only those terms get an `excluded` row under HIGHCHOL, which makes the exclusion visible in the output. A study that also lists a cholesterol include term is included.
4. **Precision sample scope.** The sample is drawn from included studies that have at least one Massachusetts site (any fetched status), because only those studies feed published metrics.
5. **Protecting the bio teammate's work.** If `burden_test/precision_sample.csv` already has any non-blank `correct` cell, a rerun keeps the file unchanged unless the user explicitly asks for a new sample (Requirement 11).
6. **Offline runs.** The recall check is the only network step. A `--offline` option skips it and leaves the existing `recall_check.json` unchanged, so grouping can be rerun and tested without network access.
7. **DEPRESSION "secondary outcome only".** `studies.csv` has no outcome fields, so this exclude rule cannot be applied from current data. It must be resolved (or recorded as a known limitation) when DEPRESSION is added. It does not affect the MVP diseases.
8. **Recall measures term coverage, using two counts.** `found_count` counts the studies our matching *finds* for a disease (any Study_Disease_Row: included, questionable or excluded). `ratio_found` = `found_count` / `ctgov_count` therefore shows whether our terms find the studies that ClinicalTrials.gov's `query.cond` search finds. `included_count` counts only `included` rows. It is lower than `found_count` by design, because our exclude rules (child-only, gestational, healthy volunteers, etc.) remove studies that ClinicalTrials.gov's search does not remove. `ratio_included` is therefore informational only. ClinicalTrials.gov's search also expands synonyms, so `ratio_found` below 1.0 can still occur. Only `ratio_found` below 0.8 is flagged, and `ratio_included` never affects `flagged`.
9. **Questionable term beats term-based exclude.** Under Requirement 4 criterion 2, a study with an Exclude_Term match and a Questionable_Term match on a value that is not an Exclude_Masked_Value is not term-excluded. The row becomes `questionable` (Requirement 7 criterion 1) so a human reviews it, rather than `excluded`.
10. **Recall check date is UTC.** The check date in `recall_check.json` is the run's UTC date, so the file does not depend on the machine's time zone.
11. **Threshold compared after rounding.** `flagged` is decided on `ratio_found` after rounding to 3 decimals (half up, computed exactly), so the value written in the file and the flag always agree (0.7995 → 0.800, not flagged). `ratio_included` is rounded the same way but is not compared with the threshold.
12. **Ratios above 1.0 are not capped.** `found_count` or `included_count` can exceed `ctgov_count` (for example when our MeSH matching finds studies the condition search misses). Both ratios are written as computed so this case stays visible.
13. **The Term_Audit drives the final term lists.** The terms in Requirement 2 criterion 3 are a minimum. The final Include_Term, Exclude_Term and Questionable_Term lists in `rules.py` are built from the Term_Audit (Requirement 14) together with inclusion_rules.md. The developer fills every disposition in `term_audit.md` by applying inclusion_rules.md, and marks any value it cannot classify unambiguously as `questionable` with a reason code. `rules.py` is built from those dispositions and used as-is, without waiting for review. The bio teammate reviews the dispositions, every Questionable_Term and its reason code afterwards. A Questionable_Term the bio teammate resolves moves to the Include_Term or Exclude_Term list in a later edit of `rules.py`.
14. **One entry for identical forms.** When the MeSH_Form and Free_Text_Form of a term have the same Normalized_Text (for example "Diabetes Insipidus" and "diabetes insipidus", or "Hypercholesterolemia" and "hypercholesterolemia"), the Rules_Config lists the term once, because Requirement 2 criterion 6 rejects duplicates. That single entry is used for both Exact_Match and Phrase_Match.
15. **Questionable masking.** A study value that matches a Questionable_Term of a disease is a Masked_Value for that disease, exactly like a value that matches an Exclude_Term, so an Include_Term match on the same value is not include evidence. Before this decision, "Pediatric Asthma" phrase-matched the Include_Term "asthma" and the study was counted as `included` for CASTHMA, even though "Pediatric Asthma" is configured as a Questionable_Term (`pediatric_label`) that needs human review. A study that also has a clean include value (one matching no Exclude_Term and no Questionable_Term of that disease) stays included. Questionable_Term matches remain candidates for the questionable rule (Requirement 7 criteria 1 and 5) and their reason codes are unchanged. Exclude masking keeps its precedence: the term-based exclude rules (Requirement 4 criteria 2 and 3) are unchanged, and the check "no Questionable_Term match on a value that is not masked" in Requirement 4 criterion 2 uses Exclude_Masked_Values only. Because Exact_Match compares whole Normalized_Text values and Requirement 2 criterion 6 forbids duplicate terms, a `meshTerms` or `ancestorTerms` value matches at most one term of a disease, so in practice only `conditions` values (Phrase_Match) are affected.
16. **HIGHCHOL recall query.** The condition search "High Cholesterol" returned a `ctgov_count` of 6 against a `found_count` of 123 (`ratio_found` 20.5), because ClinicalTrials.gov's search for that phrase does not cover studies listed under hypercholesterolemia, hyperlipidemia, dyslipidemia or LDL. The HIGHCHOL Recall_Query_Term is therefore exactly "hypercholesterolemia OR hyperlipidemia OR dyslipidemia OR LDL". Found_Count still counts `excluded` rows by design (Open Item 8), and 215 HIGHCHOL rows in the committed `study_diseases.csv` are `excluded` with `ascvd_only`, so `ratio_found` may remain above 1.0. This is expected and not capped (Open Item 12).

## Glossary

- **Mapping_Pipeline**: The Python 3.11+ command-line program started by `python -m pipeline.mapping`, described by this document.
- **Rules_Config**: The Python module `pipeline/mapping/rules.py`, containing only plain data (string, integer, list and dict literals) and no logic, that holds every disease definition, term list, reason code, recall query term and sampling seed. Editable without changing logic code. No YAML file and no YAML library (such as PyYAML) is used.
- **MeSH_Form**: The exact MeSH descriptor name for a concept, as written in `meshTerms` or `ancestorTerms` (for example "Diabetes, Gestational").
- **Free_Text_Form**: The plain-language phrase for a concept as investigators write it in `conditions` (for example "gestational diabetes").
- **Audit_Keyword**: One of the strings `asthma` (CASTHMA), `cholesterol`, `lipid`, `LDL`, `lipoprotein` (HIGHCHOL) and `diabet` (DIABETES), each assigned to the measureid shown.
- **Term_Audit**: The one-off development script and its output file `.kiro/specs/condition-grouping/term_audit.md`, which lists the most frequent `studies.csv` values containing each Audit_Keyword (Requirement 14). The Term_Audit is not part of the Mapping_Pipeline run.
- **Disease_Definition**: One entry in the Rules_Config: a PLACES measureid, a disease_label, Include_Terms, Exclude_Terms, Questionable_Terms, the Ancestor_Only_Status, and the Recall_Query_Term.
- **Supported_Measure**: One of the PLACES measureids CASTHMA, HIGHCHOL, DIABETES, BPHIGH, DEPRESSION.
- **Include_Term**: A term in a Disease_Definition whose match counts as evidence that the study is about that disease.
- **Exclude_Term**: A term in a Disease_Definition paired with an exclusion reason code (for example "gestational diabetes" → `gestational`, "prediabetes" → `prediabetes`).
- **Questionable_Term**: A term in a Disease_Definition paired with a questionable reason code, used for matches that need human review.
- **Ancestor_Only_Status**: The match_status (`included` or `questionable`) a Disease_Definition assigns when the only Include_Term matches are in `ancestorTerms`.
- **Term_Matcher**: The Mapping_Pipeline component that finds Include_Term, Exclude_Term and Questionable_Term matches in a study's `meshTerms`, `ancestorTerms` and `conditions`.
- **Normalized_Text**: A string after Unicode case folding, with runs of whitespace collapsed to one space and leading and trailing whitespace removed.
- **Phrase_Match**: A term matches a free-text condition value when the Normalized_Text of the term occurs in the Normalized_Text of the value with a word boundary (start, end, or a character that is not a letter or digit) on both sides.
- **Exact_Match**: A term matches a MeSH or ancestor value when their Normalized_Text forms are equal.
- **Exclude_Masked_Value**: A single `conditions`, `meshTerms` or `ancestorTerms` value that matches at least one Exclude_Term of a disease.
- **Masked_Value**: A single `conditions`, `meshTerms` or `ancestorTerms` value that is an Exclude_Masked_Value of a disease or matches at least one Questionable_Term of that disease (Open Item 15). A Masked_Value is not used as include evidence for that disease. Questionable_Term matches on a Masked_Value keep their reason codes.
- **Age_Parser**: The Mapping_Pipeline component that converts a `maximumAge` value into a duration in years.
- **Child_Only_Study**: A study whose parsed `maximumAge` is less than 18 years.
- **Grouping_Engine**: The Mapping_Pipeline component that combines Term_Matcher results, age and healthy-volunteer rules into one match_status per (nctId, measureid).
- **Study_Disease_Row**: One output row of `study_diseases.csv` with the columns `nctId, measureid, disease_label, match_status, exclusion_reason, matched_on, matched_term`.
- **Determining_Match**: The single match reported in `matched_on` and `matched_term` for a Study_Disease_Row, chosen as defined in Requirement 8.
- **MA_Site**: A row in `sites.csv` whose `state` is "Massachusetts" or "MA".
- **Active_Status**: One of the overallStatus values RECRUITING, NOT_YET_RECRUITING, ACTIVE_NOT_RECRUITING.
- **Recall_Checker**: The Mapping_Pipeline component that queries ClinicalTrials.gov for condition counts and writes `recall_check.json`.
- **Found_Count**: The `found_count` value of a disease: the number of distinct nctIds with a Study_Disease_Row of any match_status for that disease, an Active_Status overallStatus and at least one MA_Site.
- **Included_Count**: The `included_count` value of a disease: the number of distinct nctIds with a Study_Disease_Row of match_status `included` for that disease, an Active_Status overallStatus and at least one MA_Site.
- **Half_Up_Rounding**: Rounding a ratio to 3 decimal places with exact rational arithmetic (no floating-point error), where a value exactly halfway between two 3-decimal values rounds to the larger one (0.7995 → 0.800).
- **Recall_Query_Term**: The `query.cond` value configured per disease for the recall check.
- **Precision_Sampler**: The Mapping_Pipeline component that writes `burden_test/precision_sample.csv`.
- **HTTP_Client**: The existing Spec 1 component in `pipeline/data/http_client.py` that performs HTTPS requests to allowed hosts only (`clinicaltrials.gov`, `data.cdc.gov`) with a 60 s timeout and the 1 s, 2 s, 4 s retry policy.
- **CSV_Reader** / **CSV_Writer**: The existing Spec 1 components in `pipeline/io/` for deterministic CSV reading and writing.
- **PII_Guard**: The check, using the shared Email_Pattern and Phone_Pattern from `pipeline/patterns.py`, that every output string value contains no email address or phone number before any file is written.

## Requirements

### Requirement 1: Read existing pipeline outputs

**User Story:** As a data engineer, I want condition grouping to work from Spec 1's processed files, so that grouping is reproducible and needs no new study fetch.

#### Acceptance Criteria

1. WHEN the Mapping_Pipeline starts and the Rules_Config has passed validation (Requirement 2 criterion 5), THE Mapping_Pipeline SHALL read study data from `pipeline/processed/studies.csv` and site data from `pipeline/processed/sites.csv` as UTF-8 using the CSV_Reader, before it groups any study or sends any recall request.
2. THE Mapping_Pipeline SHALL obtain study data only from `pipeline/processed/studies.csv`, sending no request to the ClinicalTrials.gov studies endpoint for study records.
3. IF `studies.csv` or `sites.csv` is missing, cannot be opened, is not valid UTF-8, or has a header row that is not exactly the Spec 1 column list (the 18 `studies.csv` columns or the 9 `sites.csv` columns listed under "Input facts", same names in the same order), THEN THE Mapping_Pipeline SHALL write an error naming the file and the failed check to stderr, exit with a non-zero code, and leave every output file unchanged.
4. IF a cell in one of the `studies.csv` list columns (`phases`, `stdAges`, `conditions`, `interventionTypes`, `interventionNames`, `meshTerms`, `meshIds`, `ancestorTerms`, `ancestorIds`) is not a valid JSON array whose elements are all strings (the empty array `[]` is valid), THEN THE Mapping_Pipeline SHALL write an error naming the file, the line number and the column of the first such cell (and no cell content) to stderr, exit with a non-zero code, and leave every output file unchanged.
5. IF the Python version is lower than 3.11, THEN THE Mapping_Pipeline SHALL write an error naming the required version to stderr and exit with a non-zero code before reading or writing any file.
6. IF `studies.csv` has zero data rows, or any row has an empty `nctId`, or the same `nctId` appears on more than one row, THEN THE Mapping_Pipeline SHALL write an error naming the file, the failed check and the line number of the first offending row (and no cell content other than the `nctId`) to stderr, exit with a non-zero code, and leave every output file unchanged.
7. IF `sites.csv` contains rows whose `nctId` does not appear in `studies.csv`, THEN THE Mapping_Pipeline SHALL ignore those rows when determining MA_Sites, write a warning to stderr giving the count of ignored rows, and continue the run.

### Requirement 2: Rules configuration file

**User Story:** As the bio teammate, I want every matching term in one rules file, so that I can edit terms and add diseases without touching code.

#### Acceptance Criteria

1. THE Rules_Config SHALL contain every Disease_Definition, Include_Term, Exclude_Term with its reason code, Questionable_Term with its reason code, Ancestor_Only_Status, Recall_Query_Term, and the Precision_Sampler seed, and THE Mapping_Pipeline SHALL read no term, reason code, recall query term or seed from any other file or from logic code.
2. THE Rules_Config SHALL contain Disease_Definitions for CASTHMA with disease_label "Asthma", HIGHCHOL with disease_label "High cholesterol", and DIABETES with disease_label "Diabetes".
3. THE Rules_Config SHALL encode every Include and Exclude entry of `burden_test/inclusion_rules.md` for CASTHMA, HIGHCHOL and DIABETES, with at least these terms: for CASTHMA, the Include_Term "Asthma"; for DIABETES, Include_Terms covering type 1, type 2 and unspecified diabetes ("Diabetes Mellitus", "Diabetes Mellitus, Type 1", "Diabetes Mellitus, Type 2", "diabetes"), Exclude_Terms for gestational diabetes (reason `gestational`, including the MeSH term "Diabetes, Gestational" and the free-text term "gestational diabetes"), prediabetes (reason `prediabetes`, including the MeSH term "Prediabetic State" and the free-text term "prediabetes") and diabetes insipidus (reason `not_mellitus`, the term "Diabetes Insipidus", whose MeSH_Form and Free_Text_Form "diabetes insipidus" share one Normalized_Text and therefore form one entry per Open Item 14); for HIGHCHOL, Include_Terms covering hypercholesterolemia, hyperlipidemia, dyslipidemia, familial hypercholesterolemia (including the MeSH term "Hyperlipoproteinemia Type II" and the free-text term "familial hypercholesterolemia"), elevated LDL and Lp(a), plus every term required by Requirement 14 criterion 8 (including every other HIGHCHOL MeSH descriptor found in the data for the inclusion_rules.md include list), and Exclude_Terms for ASCVD and myocardial infarction (reason `ascvd_only`). The CASTHMA child-only exclusion is enforced by Requirement 5, not by an Exclude_Term.
4. THE Mapping_Pipeline SHALL process exactly the diseases defined in the Rules_Config, so that adding a Disease_Definition for BPHIGH or DEPRESSION to the Rules_Config adds that disease to `study_diseases.csv`, `recall_check.json`, `precision_sample.csv` and the stdout summary with no change to logic code.
5. WHEN the Mapping_Pipeline loads the Rules_Config, THE Mapping_Pipeline SHALL validate that: the Rules_Config contains 1 to 5 Disease_Definitions; every measureid is a Supported_Measure and appears once; every disease_label is 1 to 100 characters after Normalized_Text; every Disease_Definition has at least one Include_Term; every Include_Term, Exclude_Term, Questionable_Term and Recall_Query_Term has a non-empty Normalized_Text of 1 to 200 characters; every reason code is 1 to 40 characters, starts with a lowercase letter and contains only lowercase letters, digits and underscores; no Rules_Config reason code equals a reserved reason code (`child_only`, `unparseable_age`, `healthy_volunteers_only`, `ancestor_only`); every Ancestor_Only_Status is `included` or `questionable`; and the Precision_Sampler seed is an integer from 0 to 4,294,967,295.
6. IF a term appears more than once in the Include_Term, Exclude_Term and Questionable_Term lists of the same Disease_Definition (compared as Normalized_Text), whether in one list or across lists, THEN THE Mapping_Pipeline SHALL report a configuration error naming the measureid and the duplicated term.
7. IF Rules_Config validation fails, THEN THE Mapping_Pipeline SHALL write one error line per failed check to stderr, each naming the measureid (or "Rules_Config" for file-level and seed checks) and the failed check, exit with a non-zero code before reading `studies.csv` or `sites.csv`, send no network request, and leave every output file unchanged.
8. THE Rules_Config SHALL set the DIABETES Ancestor_Only_Status to `questionable`, the HIGHCHOL Ancestor_Only_Status to `questionable`, and the CASTHMA Ancestor_Only_Status to `included`.
9. IF `pipeline/mapping/rules.py` is missing, cannot be imported, or does not define the expected data (the Disease_Definitions and the Precision_Sampler seed under the names and with the Python types fixed in design), THEN THE Mapping_Pipeline SHALL write an error naming the Rules_Config file to stderr, exit with a non-zero code before reading `studies.csv` or `sites.csv`, send no network request, and leave every output file unchanged.
10. THE Rules_Config SHALL list every Include_Term and Exclude_Term concept that has a MeSH descriptor in its MeSH_Form (the exact descriptor, for example "Diabetes, Gestational") and in at least one Free_Text_Form (for example "gestational diabetes"), as separate entries in the same term list wherever the forms differ as Normalized_Text, with every entry of an Exclude_Term concept carrying the same reason code.
11. THE Rules_Config SHALL contain no import statement.
12. THE Rules_Config SHALL set the Recall_Query_Terms to "Asthma" for CASTHMA, exactly "hypercholesterolemia OR hyperlipidemia OR dyslipidemia OR LDL" for HIGHCHOL (Open Item 16) and "Diabetes" for DIABETES.

### Requirement 3: Case-insensitive term matching

**User Story:** As a researcher, I want studies matched on both MeSH terms and free-text conditions regardless of letter case, so that disease counts do not miss studies because of formatting.

#### Acceptance Criteria

1. THE Term_Matcher SHALL compare each Include_Term, Exclude_Term and Questionable_Term of every Disease_Definition with every value in a study's `meshTerms` and `ancestorTerms` using Exact_Match, so that the term "Diabetes Mellitus" matches the value "diabetes mellitus" and does not match the value "Diabetes Mellitus, Type 2".
2. THE Term_Matcher SHALL compare each Include_Term, Exclude_Term and Questionable_Term of every Disease_Definition with every value in a study's `conditions` using Phrase_Match, so that the term "asthma" matches the values "Severe Asthma" and "Asthma, Exercise-Induced" and does not match the value "Asthmatic Bronchitis", and the term "type 2 diabetes" matches the value "Type  2 Diabetes Mellitus".
3. THE Term_Matcher SHALL record each match with the measureid, the term kind (include, exclude or questionable), the Rules_Config term, the source (`mesh` for `meshTerms`, `ancestor` for `ancestorTerms`, `condition_text` for `conditions`), and the full matched study list value exactly as written in `studies.csv` (not normalized and not only the matched substring), recording one match per distinct combination of these five fields even when the same value appears more than once in a list.
4. FOR ALL studies and terms, changing the letter case of any study value or Rules_Config term, or adding leading, trailing or extra internal whitespace next to existing whitespace, SHALL produce the same set of matches apart from the recorded study value text (case- and whitespace-insensitivity property).
5. THE Term_Matcher SHALL search only the `meshTerms`, `ancestorTerms` and `conditions` columns, so that terms appearing only in other columns (for example `briefTitle` or `interventionNames`) produce no match, and a list cell holding an empty JSON array (`[]`) produces no match.
6. IF a study list value has an empty Normalized_Text, THEN THE Term_Matcher SHALL skip that value and record no match for it.
7. WHEN the Term_Matcher finds no Include_Term, Exclude_Term or Questionable_Term match for a study and a disease, THE Grouping_Engine SHALL write no Study_Disease_Row for that (nctId, measureid) pair.

### Requirement 4: Exclude rules

**User Story:** As the bio teammate, I want every exclude rule from inclusion_rules.md applied, so that studies outside the PLACES measure definition are not counted.

#### Acceptance Criteria

1. WHEN a single `conditions`, `meshTerms` or `ancestorTerms` value of a study matches at least one Exclude_Term or at least one Questionable_Term of a disease, THE Grouping_Engine SHALL treat that value as a Masked_Value for that disease only, use none of the Include_Term matches on that value as include evidence for that disease, and leave the same value usable as include evidence for every other disease. Questionable_Term matches on a value that is not an Exclude_Masked_Value SHALL remain candidates for Requirement 7 criteria 1 and 5 with their configured reason codes (Open Item 15), so that a study listing only "Pediatric Asthma" (which phrase-matches the Include_Term "asthma" and the Questionable_Term "Pediatric Asthma") gets `questionable` with `pediatric_label` for CASTHMA, and a study listing both "Pediatric Asthma" and "Asthma" is included.
2. IF a study has at least one Exclude_Term match for a disease, has no Include_Term match for that disease on a value that is not a Masked_Value (including the case of zero Include_Term matches), and has no Questionable_Term match for that disease on a value that is not an Exclude_Masked_Value, THEN THE Grouping_Engine SHALL assign match_status `excluded` with exclusion_reason set to the reason code of the Exclude_Term in the Determining_Match chosen per Requirement 8 criteria 6 and 8, unless Requirement 5 criterion 3 assigns `child_only` or Requirement 6 criterion 1 assigns `healthy_volunteers_only` (so that a HIGHCHOL study matching only "Myocardial Infarction" gets `excluded` with `ascvd_only`).
3. IF a study has at least one Exclude_Term match for a disease in `conditions` or `meshTerms`, and every Include_Term match for that disease on a value that is not a Masked_Value is in `ancestorTerms`, and at least one such `ancestorTerms` Include_Term match exists, THEN THE Grouping_Engine SHALL assign match_status `excluded` with exclusion_reason set to the reason code of the Exclude_Term match chosen from the `conditions` and `meshTerms` matches only (ordered per Requirement 8 criterion 8: source order `mesh` then `condition_text`, then lowest Unicode code point order of the matched value, then of the matched term), regardless of the Disease_Definition's Ancestor_Only_Status and of any Questionable_Term matches, unless Requirement 5 criterion 3 assigns `child_only` or Requirement 6 criterion 1 assigns `healthy_volunteers_only` (so that a study listing "Gestational Diabetes" with ancestor "Diabetes Mellitus" gets `excluded` with `gestational`). A study with no Include_Term match on a value that is not a Masked_Value in any column is decided by criterion 2, not this criterion, so criteria 2 and 3 never both apply to the same (nctId, measureid) pair.
4. WHEN a study has at least one Include_Term match for a disease on a `conditions` or `meshTerms` value that is not a Masked_Value (a value matching no Exclude_Term and no Questionable_Term of that disease), THE Grouping_Engine SHALL treat that match as include evidence and assign no `excluded` status under criteria 2 or 3 for that disease, however many other values of the study match Exclude_Terms (any listed condition matches, per inclusion_rules.md), so that a study listing both "Type 2 Diabetes" and "Gestational Diabetes" has include evidence for DIABETES and its final status follows Requirements 5 and 7.
5. WHEN a study's Exclude_Term matches for a disease are all in `ancestorTerms` and its only include evidence for that disease is an Include_Term match on an `ancestorTerms` value that is not a Masked_Value, THE Grouping_Engine SHALL assign the status given by the Disease_Definition's Ancestor_Only_Status under Requirement 7 criteria 2 and 3, applying neither criterion 2 nor criterion 3 of this requirement.
6. FOR ALL studies whose only Include_Term matches for a disease are on Masked_Values, whether masked by an Exclude_Term or by a Questionable_Term (for example a study listing only "Gestational Diabetes" for DIABETES, or only "Pediatric Asthma" for CASTHMA), THE Grouping_Engine SHALL assign match_status `excluded` or `questionable` and never `included` (excluded-term property).
7. FOR ALL studies and diseases, adding a study value that matches an Exclude_Term and no Include_Term of that disease SHALL NOT change that study's match_status for that disease from `excluded` or `questionable` to `included` (exclude-monotonicity property).
8. WHEN the Mapping_Pipeline runs on the committed `pipeline/processed/studies.csv` with the committed Rules_Config, THE Grouping_Engine SHALL assign a match_status other than `included` to the CASTHMA rows of NCT04278404, NCT06538376 and NCT06903897 and to the DIABETES rows of NCT05723445, NCT06449677 and NCT07688070, and SHALL keep match_status `included` for the DIABETES and HIGHCHOL rows of NCT06903897 (verification example for criterion 1). The expected rows are: NCT06538376 CASTHMA `questionable` with `overlap_syndrome`; NCT05723445, NCT06449677 and NCT07688070 DIABETES `questionable` with `secondary_cause`; NCT04278404 and NCT06903897 CASTHMA `excluded` with `healthy_volunteers_only`, because both studies have `healthyVolunteers` = `true` and their only direct CASTHMA include values ("Asthma in Children", "Pediatric Asthma") are Masked_Values (Requirement 6 criterion 1).

### Requirement 5: Child-only studies

**User Story:** As a researcher, I want child-only studies left out of every disease, so that counts match the adults-only PLACES prevalence.

#### Acceptance Criteria

1. WHEN `maximumAge`, after removing leading and trailing whitespace, consists of one or more ASCII digits, exactly one space, and a unit of Year, Years, Month, Months, Week, Weeks, Day, Days, Hour, Hours, Minute or Minutes (unit compared case-insensitively, singular and plural forms accepted for any number), THE Age_Parser SHALL convert the value to years using 1 year = 12 months = 52.1775 weeks = 365.25 days = 8,766 hours = 525,960 minutes.
2. WHEN `maximumAge` is empty or contains only whitespace, THE Age_Parser SHALL report no upper age limit, and THE Grouping_Engine SHALL treat the study as not a Child_Only_Study.
3. WHEN a study is a Child_Only_Study and has at least one Include_Term, Exclude_Term or Questionable_Term match for a disease, THE Grouping_Engine SHALL assign match_status `excluded` with exclusion_reason `child_only` for that disease, taking precedence over every rule of Requirements 4, 6 and 7, and SHALL choose the Determining_Match per Requirement 8 criterion 6 case (b): an Include_Term match on a value that is not a Masked_Value if one exists, otherwise the first of all the study's matches for that disease in the Requirement 8 criterion 8 order.
4. IF `maximumAge` is non-empty and does not have the form described in criterion 1 (for example a negative number, a decimal number, a missing unit, an unlisted unit, or no space between number and unit), THEN THE Grouping_Engine SHALL assign match_status `questionable` with exclusion_reason `unparseable_age` to every disease the study has at least one term match for, replacing any `included` status and any other questionable reason code, unless Requirement 6 criterion 1 assigns `healthy_volunteers_only` or Requirement 4 criterion 2 or 3 assigns a term-based `excluded` (precedence per Requirement 7 criterion 6).
5. FOR ALL studies with a parsed `maximumAge` below 18 years, THE Grouping_Engine SHALL assign no `included` row and SHALL assign exclusion_reason `child_only` to every Study_Disease_Row of that study (child-only property).
6. FOR ALL `maximumAge` strings of the form described in criterion 1, THE Age_Parser SHALL classify the study as a Child_Only_Study exactly when the converted age is strictly less than 18 years, with the comparison computed without floating-point rounding error, so that "17 Years", "215 Months", "939 Weeks", "6574 Days", "157787 Hours" and "0 Years" are child-only, and "18 Years", "216 Months", "940 Weeks", "6575 Days" and "157788 Hours" are not.
7. THE Grouping_Engine SHALL decide whether a study is a Child_Only_Study from `maximumAge` alone, ignoring `minimumAge` and `stdAges`.

### Requirement 6: Healthy-volunteer studies

**User Story:** As the bio teammate, I want healthy-volunteer studies without a matching patient condition excluded with a reason, so that they are not counted as disease studies.

#### Acceptance Criteria

1. IF a study has `healthyVolunteers` = `true`, has at least one term match for a disease, and has no Include_Term match for that disease on a value in `conditions` or `meshTerms` that is not a Masked_Value, THEN THE Grouping_Engine SHALL assign match_status `excluded` with exclusion_reason `healthy_volunteers_only` for that disease. This applies when the study's remaining matches are only `ancestorTerms` Include_Term matches (whatever the Ancestor_Only_Status), Questionable_Term matches, Exclude_Term matches, or Include_Term matches on Masked_Values, including values masked by a Questionable_Term, so that a healthy-volunteer study whose only direct Include_Term matches are on values such as "Pediatric Asthma" gets `healthy_volunteers_only`.
2. WHILE a study is a Child_Only_Study, THE Grouping_Engine SHALL assign exclusion_reason `child_only` (Requirement 5 criterion 3) instead of `healthy_volunteers_only`. In every other case covered by criterion 1, `healthy_volunteers_only` SHALL take precedence over the Exclude_Term reason codes of Requirement 4, the Questionable_Term reason codes and `ancestor_only` of Requirement 7, and `unparseable_age` of Requirement 5 criterion 4.
3. WHEN the Grouping_Engine assigns exclusion_reason `healthy_volunteers_only`, THE Grouping_Engine SHALL choose the Determining_Match from all of the study's term matches for that disease, including Include_Term matches on Masked_Values, ordered per Requirement 8 criterion 8 (source order `mesh`, then `ancestor`, then `condition_text`, then the lowest Unicode code point order of the matched value, then of the matched term).
4. WHEN a study has `healthyVolunteers` = `true` and has at least one Include_Term match for a disease on a value in `conditions` or `meshTerms` that is not a Masked_Value (a value matching no Exclude_Term and no Questionable_Term of that disease), THE Grouping_Engine SHALL produce a Study_Disease_Row for that disease identical to the row it would produce with `healthyVolunteers` = `false`.
5. WHEN `healthyVolunteers` is `false` or empty, THE Grouping_Engine SHALL apply no healthy-volunteer rule and SHALL assign no exclusion_reason `healthy_volunteers_only`.
6. IF a `healthyVolunteers` cell in `studies.csv` is not exactly `true`, `false` or empty (compared case-sensitively), THEN THE Mapping_Pipeline SHALL write an error naming the file, line number and column (and no cell content) to stderr, exit with a non-zero code, and leave every output file unchanged.
7. FOR ALL studies with `healthyVolunteers` = `true` and no Include_Term match for a disease on a non-Masked_Value in `conditions` or `meshTerms` (Masked_Values covering both Exclude_Term and Questionable_Term matches), THE Grouping_Engine SHALL assign no `included` row for that disease (healthy-volunteer property).

### Requirement 7: Questionable matches

**User Story:** As a researcher, I want unclear matches flagged rather than counted, so that published counts contain only clear matches.

#### Acceptance Criteria

1. IF a study has at least one Questionable_Term match for a disease on a value that is not an Exclude_Masked_Value (including a value that also matches an Include_Term), has no include evidence for that disease (no Include_Term match on a value that is not a Masked_Value in `conditions` or `meshTerms`, and no ancestor match treated as include evidence under criterion 3), and no rule of Requirement 4, 5 or 6 assigns `excluded`, THEN THE Grouping_Engine SHALL assign match_status `questionable` with exclusion_reason set to the reason code of the Questionable_Term in the Determining_Match.
2. IF a study's only Include_Term matches for a disease that are not on a Masked_Value are in `ancestorTerms`, and the Disease_Definition's Ancestor_Only_Status is `questionable`, and no rule of Requirement 4, 5 or 6 assigns `excluded`, THEN THE Grouping_Engine SHALL assign match_status `questionable` with exclusion_reason `ancestor_only`.
3. IF a study's only Include_Term matches for a disease that are not on a Masked_Value (masked by an Exclude_Term or a Questionable_Term, Requirement 4 criterion 1) are in `ancestorTerms`, and the Disease_Definition's Ancestor_Only_Status is `included`, THEN THE Grouping_Engine SHALL treat those ancestor matches as include evidence for that disease, with the result still subject to the `excluded` rules of Requirements 4, 5 and 6.
4. WHEN a study has include evidence for a disease (Include_Term matches on values that are not Masked_Values, per Requirement 4 criteria 1 and 4 and criterion 3), no rule of Requirement 4, 5 or 6 assigns `excluded`, and Requirement 5 criterion 4 does not assign `questionable` with `unparseable_age`, THE Grouping_Engine SHALL assign match_status `included` with an empty exclusion_reason, even if the study also has Questionable_Term matches for that disease on other values.
5. IF both criterion 1 and criterion 2 apply to the same (nctId, measureid) pair, THEN THE Grouping_Engine SHALL assign match_status `questionable` with the reason of the Determining_Match chosen under Requirement 8 criteria 6 and 8 from the Questionable_Term and ancestor matches (source order `mesh`, `ancestor`, `condition_text`, then lowest Unicode code point order of the matched value).
6. THE Grouping_Engine SHALL apply status rules for each (nctId, measureid) pair in this order of precedence, using the first rule that applies: `excluded` with `child_only` (Requirement 5 criterion 3); `excluded` with `healthy_volunteers_only` (Requirement 6 criterion 1); term-based `excluded` (Requirement 4 criteria 2 and 3); `questionable` with `unparseable_age` (Requirement 5 criterion 4); `included` (criterion 4); `questionable` with a Questionable_Term reason or `ancestor_only` (criteria 1, 2 and 5).
7. FOR ALL Study_Disease_Rows with match_status `questionable`, the exclusion_reason SHALL be non-empty and equal to either `ancestor_only`, `unparseable_age`, or a Questionable_Term reason code configured in the Rules_Config for that measureid (questionable-reason property).
8. FOR ALL (nctId, measureid) pairs with no include evidence as defined in criteria 3 and 4 and Requirement 4 criteria 1 and 4 (so every Include_Term match is on a Masked_Value, or is an `ancestorTerms` match under Ancestor_Only_Status `questionable`), THE Grouping_Engine SHALL assign a match_status other than `included` (no-evidence-not-included property).

### Requirement 8: Study_Disease_Row content

**User Story:** As the scoring developer, I want each output row to follow the data contract exactly, so that Spec 3 can count eligible studies without reinterpreting matches.

#### Acceptance Criteria

1. THE Grouping_Engine SHALL produce exactly one Study_Disease_Row for each (nctId, measureid) pair where the study has at least one Include_Term, Exclude_Term or Questionable_Term match for a Disease_Definition in the Rules_Config. No two rows SHALL share the same (nctId, measureid) pair, and one study MAY have rows for several diseases.
2. THE Grouping_Engine SHALL set `measureid` to the measureid of the Disease_Definition and `disease_label` to that Disease_Definition's disease_label character for character. It SHALL set `match_status` to exactly one of the lowercase values `included`, `questionable` or `excluded`.
3. WHEN match_status is `included`, THE Grouping_Engine SHALL set `exclusion_reason` to the empty string.
4. WHEN match_status is `questionable` or `excluded`, THE Grouping_Engine SHALL set `exclusion_reason` to a non-empty reason code that is one of these: a reason code of an Exclude_Term or Questionable_Term in that Disease_Definition, or one of `child_only`, `healthy_volunteers_only`, `ancestor_only` and `unparseable_age`.
5. THE Grouping_Engine SHALL set `matched_on` to the source of the Determining_Match (`mesh`, `ancestor` or `condition_text`, as defined in Requirement 3 criterion 3). It SHALL set `matched_term` to the study value of the Determining_Match exactly as written in `studies.csv`, keeping its original letter case and spacing, and not to its Normalized_Text or the Rules_Config term. Both cells SHALL be non-empty.
6. THE Grouping_Engine SHALL choose the Determining_Match from the candidate matches for the assigned status, as follows:
   - (a) `included`: the Include_Term matches counted as include evidence under Requirements 4 and 7, none of which is on a Masked_Value.
   - (b) `excluded` with `child_only` or questionable with `unparseable_age`: the Include_Term matches that are not on a Masked_Value (masked by an Exclude_Term or a Questionable_Term), or every term match for that disease if there is no such match.
   - (c) `excluded` under Requirement 4 criterion 2: the Exclude_Term matches.
   - (d) `excluded` under Requirement 4 criterion 3: the Exclude_Term matches in `conditions` or `meshTerms` only, excluding every `ancestorTerms` match (as stated in Requirement 4 criterion 3).
   - (e) `excluded` with `healthy_volunteers_only`: every term match for that disease, of any kind and any source (as stated in Requirement 6 criterion 3).
   - (f) `questionable` under Requirement 7 criterion 1: the Questionable_Term matches on values that are not Exclude_Masked_Values, including those on values that also match an Include_Term.
   - (g) `questionable` with `ancestor_only`: the Include_Term matches in `ancestorTerms`.

   For cases (c), (d) and (f), the `exclusion_reason` SHALL be the reason code that the Rules_Config pairs with the matched term of the Determining_Match.
7. FOR ALL Study_Disease_Rows, the `nctId` SHALL exist in `studies.csv` (referential-integrity property).
8. WHEN more than one candidate match from criterion 6 exists, THE Grouping_Engine SHALL pick the Determining_Match using these keys in order: first source, in the order `mesh`, then `ancestor`, then `condition_text`; then the matched study value, lowest by Unicode code point; then the Normalized_Text of the matched Rules_Config term, lowest by Unicode code point. The same inputs then always produce the same `matched_on`, `matched_term` and `exclusion_reason`.
9. FOR ALL Study_Disease_Rows, `matched_term` SHALL equal a value in the study's `studies.csv` column named by `matched_on` (`meshTerms` for `mesh`, `ancestorTerms` for `ancestor`, `conditions` for `condition_text`). That value SHALL match, under the Term_Matcher rules of Requirement 3, at least one term of the row's Disease_Definition (match-consistency property).

### Requirement 9: Write study_diseases.csv

**User Story:** As the scoring developer, I want a deterministic, round-trippable `study_diseases.csv`, so that reruns produce identical files and diffs show only real changes.

#### Acceptance Criteria

1. THE Mapping_Pipeline SHALL write `pipeline/processed/study_diseases.csv` with exactly one header row `nctId,measureid,disease_label,match_status,exclusion_reason,matched_on,matched_term` in that order, followed by one data row per Study_Disease_Row, each with exactly 7 cells.
2. WHEN no study has a term match for any disease, THE Mapping_Pipeline SHALL write `study_diseases.csv` containing only the header row and exit with code 0.
3. THE Mapping_Pipeline SHALL encode `study_diseases.csv` as UTF-8 without a byte order mark, end every line (including the last) with a single LF and no CR, and write non-ASCII characters as UTF-8 text, using the Spec 1 CSV_Writer conventions.
4. THE Mapping_Pipeline SHALL enclose a cell in double quotes exactly when the cell contains a comma, a double quote, a CR or an LF, SHALL double every double quote inside a quoted cell, and SHALL write every other cell, including an empty cell, without quotes.
5. THE Mapping_Pipeline SHALL sort the rows of `study_diseases.csv` by `nctId`, then by `measureid`, comparing cell strings by Unicode code point.
6. FOR ALL valid sets of Study_Disease_Rows, including values that are empty or contain commas, double quotes, CR, LF or non-ASCII characters, writing with the CSV_Writer and then reading with the CSV_Reader SHALL produce rows whose 7 cell strings are equal to the originals (round-trip property).
7. FOR ALL inputs, running the Mapping_Pipeline twice on byte-identical `studies.csv`, `sites.csv` and Rules_Config, with the `--offline` option or with identical `totalCount` values returned by ClinicalTrials.gov, SHALL produce a byte-identical `study_diseases.csv`, a byte-identical `precision_sample.csv`, and a `recall_check.json` that is identical except for the check date (determinism property).
8. FOR ALL permutations of the data row order of `studies.csv`, the Mapping_Pipeline SHALL produce a byte-identical `study_diseases.csv` (order-independence property).
9. IF the PII_Guard finds an Email_Pattern or Phone_Pattern match in any cell value to be written to `study_diseases.csv`, `precision_sample.csv` or `recall_check.json`, THEN THE Mapping_Pipeline SHALL write an error to stderr naming the output file, the column (or JSON key) and the nctId (or measureid for `recall_check.json`) and no cell content, exit with a non-zero code, and leave every output file unchanged.
10. THE Mapping_Pipeline SHALL run the PII_Guard on every output file's final content and finish all grouping, recall and sampling steps before replacing any of `study_diseases.csv`, `recall_check.json` or `precision_sample.csv`.
11. THE Mapping_Pipeline SHALL write each output file to a temporary file in its target directory and replace the target only when that file is fully written, so that no partially written `study_diseases.csv`, `recall_check.json` or `precision_sample.csv` exists at its target path at any time.
12. IF any step of a run fails, including a file write error, THEN THE Mapping_Pipeline SHALL write an error naming the affected file and the operating-system error type to stderr, exit with a non-zero code, remove its temporary files, and leave `study_diseases.csv`, `recall_check.json` and `precision_sample.csv` byte-for-byte unchanged.

### Requirement 10: Recall check

**User Story:** As the team, I want our included counts compared with ClinicalTrials.gov's own condition search, so that we can see whether matching misses many studies.

#### Acceptance Criteria

1. THE Recall_Checker SHALL compute `found_count` for each Disease_Definition in the Rules_Config as the number of distinct nctIds that meet all three conditions: a Study_Disease_Row of any match_status (`included`, `questionable` or `excluded`) for that disease, a `studies.csv` overallStatus that is an Active_Status, and at least one MA_Site of any `siteStatus`. Each study SHALL be counted once however many MA_Sites it has, and `found_count` SHALL be 0 when no study meets these conditions. THE Recall_Checker SHALL compute `included_count` by the same rule, counting only Study_Disease_Rows with match_status `included`, so that `included_count` is at most `found_count`.
2. WHEN the Mapping_Pipeline runs without the `--offline` option, THE Recall_Checker SHALL send exactly one GET request per Disease_Definition through the HTTP_Client, in ascending measureid order, to `https://clinicaltrials.gov/api/v2/studies` with the parameters `query.cond=<Recall_Query_Term>`, `query.locn=Massachusetts`, `filter.overallStatus=RECRUITING,NOT_YET_RECRUITING,ACTIVE_NOT_RECRUITING`, `countTotal=true`, `pageSize=1` and `fields=NCTId`, using the HTTP_Client's 60 s timeout and its 1 s, 2 s, 4 s retry policy (at most 4 attempts per request). It SHALL then read `ctgov_count` from the response `totalCount`.
3. THE Recall_Checker SHALL compute `ratio_found` as `found_count / ctgov_count` and `ratio_included` as `included_count / ctgov_count`, each rounded to 3 decimal places by Half_Up_Rounding. Neither ratio SHALL be capped at 1.0. WHEN `ctgov_count` is 0, THE Recall_Checker SHALL set both `ratio_found` and `ratio_included` to null.
4. THE Recall_Checker SHALL set `flagged` to true when the rounded `ratio_found` is below 0.800 or is null, and to false when the rounded `ratio_found` is 0.800 or higher, using `ratio_included` for no part of the decision. For example, a `ratio_found` of 0.7995 rounds to 0.800 and is not flagged, a `ratio_found` of 0.7994 rounds to 0.799 and is flagged, and a `ratio_found` of 0.9 with a `ratio_included` of 0.1 is not flagged.
5. WHEN every recall request has succeeded, THE Recall_Checker SHALL write `pipeline/processed/recall_check.json` as UTF-8 without BOM, with LF line endings and keys in a fixed order. The file SHALL contain the check date as the run's UTC date in `YYYY-MM-DD` form, the threshold 0.8, and exactly one entry per Disease_Definition sorted by measureid. Each entry SHALL hold, in this order, `measureid`, `disease_label`, `recall_query_term`, `found_count`, `included_count`, `ctgov_count`, `ratio_found`, `ratio_included`, `flagged`, and `request_url` (the full percent-encoded request URL). The output SHALL be byte-identical across runs with identical inputs and identical `ctgov_count` values on the same UTC date.
6. WHEN one or more diseases have `flagged` = true, THE Mapping_Pipeline SHALL write one warning line per flagged disease to stderr containing the measureid, `found_count`, `included_count`, `ctgov_count` and `ratio_found` (written as `null` when null). It SHALL still write all outputs and exit with code 0.
7. IF a recall request still fails after the HTTP_Client retry policy, or returns a non-success HTTP status, or returns a body that is not valid JSON, or has a `totalCount` that is missing, not an integer or negative, THEN THE Mapping_Pipeline SHALL write an error to stderr naming the measureid and request URL (and no response body content). It SHALL exit with a non-zero code without writing any output file, leaving `study_diseases.csv`, `recall_check.json` and `precision_sample.csv` byte-for-byte unchanged.
8. WHERE the `--offline` option is given, THE Mapping_Pipeline SHALL send no network request, write no flagged `ratio_found` warnings, and leave `recall_check.json` byte-for-byte unchanged, while still writing `study_diseases.csv` and running the Precision_Sampler.
9. IF the `--offline` option is given and `pipeline/processed/recall_check.json` does not exist, THEN THE Mapping_Pipeline SHALL create no `recall_check.json`, write a notice to stderr saying the recall check was skipped and no recall file exists, and exit with code 0 if all other steps succeed.

### Requirement 11: Precision sample

**User Story:** As the bio teammate, I want a fixed random sample of included studies per disease, so that I can hand-check matching precision.

#### Acceptance Criteria

1. THE Precision_Sampler SHALL select, for each Disease_Definition in the Rules_Config, up to 20 distinct nctIds from the candidate set: the nctIds that have a Study_Disease_Row with match_status `included` for that measureid and at least one MA_Site, with any `siteStatus`. The selection SHALL use a seeded pseudo-random generator, initialised with the Rules_Config seed and applied to the candidates sorted by nctId in Unicode code point order.
2. IF a disease has fewer than 20 candidates, including zero, THEN THE Precision_Sampler SHALL include every candidate and write to stderr a warning naming the measureid and the candidate count. A disease with zero candidates SHALL get no rows in `precision_sample.csv`.
3. THE Precision_Sampler SHALL write `burden_test/precision_sample.csv` with the header `nctId,measureid,briefTitle,conditions,matched_term,source_url,correct`. The file SHALL have exactly one row per selected (nctId, measureid) pair, follow the CSV conventions of Requirement 9 criteria 3 and 4, and sort rows by `measureid` then `nctId` in Unicode code point order. If no disease has any candidates, the file SHALL contain only the header row.
4. THE Precision_Sampler SHALL copy `briefTitle`, `conditions` (as the JSON array string) and `source_url` from the matching `studies.csv` row, and `matched_term` from the Study_Disease_Row with the same nctId and measureid. Copied values SHALL be unchanged from their source. The `correct` cell SHALL be the empty string.
5. FOR ALL Rules_Config seeds and inputs, running the Precision_Sampler twice on the same `studies.csv`, `sites.csv` and Rules_Config SHALL select the same nctIds and produce a byte-identical `precision_sample.csv`. The selection for one disease SHALL depend only on the seed and that disease's sorted candidate list, so adding or removing another Disease_Definition does not change it (deterministic-sample property).
6. IF `burden_test/precision_sample.csv` exists, the `--resample` option is not given, and at least one `correct` cell contains a character other than whitespace, THEN THE Precision_Sampler SHALL keep the file byte-for-byte unchanged and write to stderr a notice naming the file and the number of filled `correct` cells. THE Mapping_Pipeline SHALL still write its other outputs and exit with code 0 if no other error occurs.
7. WHEN the `--resample` option is given, or `burden_test/precision_sample.csv` does not exist, or every `correct` cell in it is empty or whitespace-only, THE Precision_Sampler SHALL write a new `precision_sample.csv` atomically per Requirement 9 criterion 11, replacing any existing file. This SHALL happen whether or not the `--offline` option is given.
8. IF `burden_test/precision_sample.csv` exists, the `--resample` option is not given, and the file cannot be read by the CSV_Reader or its header differs from the header in criterion 3, THEN THE Mapping_Pipeline SHALL write an error naming the file to stderr, exit with a non-zero code, and leave every output file unchanged.
9. IF the Rules_Config seed is missing or is not an integer from 0 to 4,294,967,295 inclusive, THEN THE Mapping_Pipeline SHALL report a configuration error as defined in Requirement 2 criterion 7, naming the seed as the failed check.

### Requirement 12: Entry point and run output

#### Acceptance Criteria

1. WHEN a user runs `python -m pipeline.mapping`, THE Mapping_Pipeline SHALL run these steps in this order: the Python version check (Requirement 1 criterion 5), load and validate the Rules_Config, read `studies.csv` and `sites.csv`, group studies, run the Recall_Checker (skipped under `--offline`), run the Precision_Sampler, run the PII_Guard on every value to be written, and write the output files.

3. THE Mapping_Pipeline SHALL accept only the options `--offline` (Requirement 10 criterion 8) and `--resample` (Requirement 11 criterion 6). Each option takes no value, and the two options may be given together in either order.
4. IF the command line contains an option other than `--offline` or `--resample`, or a positional argument, THEN THE Mapping_Pipeline SHALL write a usage message to stderr, exit with code 2, read no input file, send no network request, and leave every output file unchanged.
5. IF any step listed in criterion 1 fails, THEN THE Mapping_Pipeline SHALL run no later step, write one error message to stderr, exit with code 1, and leave `study_diseases.csv`, `recall_check.json` and `precision_sample.csv` byte-for-byte unchanged. 6. WHEN every output file has been written, THE Mapping_Pipeline SHALL write a summary to stdout and then exit with code 0. The summary SHALL contain one block per disease, sorted by measureid by Unicode code point. Each block SHALL give the measureid, the count of `included`, `questionable` and `excluded` Study_Disease_Rows (showing 0 for any status with no rows), and the count of rows for each exclusion_reason that has at least one row, sorted by reason code.
7. WHILE a run produces only warnings or notices (a flagged `ratio_found`, fewer than 20 precision sample candidates, or a precision sample kept unchanged), THE Mapping_Pipeline SHALL complete every step in criterion 1 and exit with code 0.
8. THE Mapping_Pipeline SHALL limit stdout and stderr output to nctIds, counts, measureids, reason codes, file names, column names, line numbers, URLs and dates, and SHALL limit file output to those values plus study fields copied from `studies.csv`. No output SHALL contain contact names, email addresses or phone numbers.
9. THE Mapping_Pipeline SHALL list every third-party package it imports that is not already in `requirements.txt` in `requirements.txt` with an exact pinned version (`==`).

### Requirement 13: Tests

**User Story:** As a developer, I want property-based tests of the matching rules, so that rule edits cannot silently break the inclusion logic.

#### Acceptance Criteria

1. THE test suite SHALL use pytest as the runner and Hypothesis for properties, with every Hypothesis property set to run at least 100 generated examples under every settings profile used by the suite, and SHALL pass with exit code 0 when `pytest` is run from the repository root with no network access.
2. THE test suite SHALL include Hypothesis properties for case-insensitive matching (Requirement 3 criterion 4), excluded terms never included (Requirement 4 criterion 6), questionable-masked include evidence never included while clean direct include evidence is included (Requirement 4 criteria 1, 4 and 6, Requirement 7 criterion 4), exclude monotonicity (Requirement 4 criterion 7), child-only studies never included (Requirement 5 criterion 5), healthy-volunteer studies without patient-condition evidence never included (Requirement 6 criterion 7), questionable rows always carrying a valid reason (Requirement 7 criterion 7), every output nctId existing in `studies.csv` (Requirement 8 criterion 7), match consistency of `matched_on` and `matched_term` (Requirement 8 criterion 9), deterministic output (Requirement 9 criteria 7 and 8), and deterministic precision sample selection (Requirement 11 criterion 5). The generated studies SHALL cover mixed letter case in study values and Rules_Config terms, `maximumAge` values in each of the 12 units of Requirement 5 criterion 1 as well as empty values, and `healthyVolunteers` values `true`, `false` and empty.
3. THE test suite SHALL include a round-trip property for `study_diseases.csv` (Requirement 9 criterion 6) and a property for the Age_Parser threshold (Requirement 5 criterion 6). The Age_Parser tests SHALL also include example cases asserting that "17 Years", "215 Months" and "939 Weeks" are child-only and that "18 Years" and "216 Months" are not.

Each example SHALL use one representative study and assert the expected `match_status`, `exclusion_reason`, `matched_on` and `matched_term`.
5. WHEN the test suite tests the Recall_Checker, THE test suite SHALL use a stub HTTP_Client that returns a configured `totalCount`, and SHALL assert the request URL parameters of Requirement 10 criterion 2, `found_count`, `included_count`, `ratio_found` and `ratio_included` rounded to 3 decimals by Half_Up_Rounding, both ratios = null when `ctgov_count` is 0, `flagged` = true for `ratio_found` 0.799 and null, `flagged` = false for `ratio_found` 0.8, and `flagged` independent of `ratio_included` (for example `ratio_found` 0.9 with `ratio_included` 0.1 is not flagged).

### Requirement 14: Term audit

**User Story:** As the bio teammate, I want a list of the disease-related values that actually occur in the study data, so that the Rules_Config term lists cover the real MeSH and free-text spellings and no ambiguous value is silently counted or dropped.

#### Acceptance Criteria

1. WHEN the Term_Audit runs, THE Term_Audit SHALL, for each Audit_Keyword and separately for each of the `meshTerms`, `ancestorTerms` and `conditions` columns of `pipeline/processed/studies.csv`, list the 40 most frequent distinct study list values (exactly as written in `studies.csv`) whose Unicode case-folded form contains the case-folded Audit_Keyword as a substring, so that the keyword `LDL` lists "LDL Cholesterol" and "VLDL" and the keyword `diabet` lists "Diabetes Mellitus, Type 2" and "Diabetic Retinopathy". When more than 40 values qualify, THE Term_Audit SHALL list exactly the first 40 in the order of criterion 3, and SHALL skip every value whose Normalized_Text is empty.
2. THE Term_Audit SHALL give each listed value a count equal to the number of distinct studies whose list in that column contains the value exactly as written in `studies.csv`, counting a study once even when the value appears more than once in its list, and counting values that differ only in letter case or whitespace as separate values.
3. THE Term_Audit SHALL order the values of each (Audit_Keyword, column) list by count, highest first, and break ties by the value in ascending Unicode code point order.
4. IF fewer than 40 distinct values in a column contain an Audit_Keyword, THEN THE Term_Audit SHALL list every such value, and SHALL write "no values" in place of the table for a (Audit_Keyword, column) list with zero values.
5. THE Term_Audit SHALL save its output as `.kiro/specs/condition-grouping/term_audit.md`, encoded as UTF-8 without a byte order mark with LF line endings, containing the lowercase hexadecimal SHA-256 digest of the bytes of the `studies.csv` file it read, the total number of `studies.csv` data rows, and one table per (Audit_Keyword, column) pair in Audit_Keyword order `asthma`, `cholesterol`, `lipid`, `LDL`, `lipoprotein`, `diabet` and column order `meshTerms`, `ancestorTerms`, `conditions`. Each table SHALL have one row per listed value with the columns rank (1 to 40), value, count, measureid of the Audit_Keyword, disposition, and reason code or note. THE Term_Audit SHALL write the disposition and reason/note cells empty, write every `|` inside a value as `\|`, and write no timestamp or other run-dependent text.
6. FOR ALL `studies.csv` inputs, running the Term_Audit twice on byte-identical `studies.csv` with no existing `term_audit.md` SHALL produce a byte-identical `term_audit.md`, and permuting the data row order of `studies.csv` SHALL produce the same tables (determinism property).
7. WHEN the Term_Audit has written `term_audit.md` and before `pipeline/mapping/rules.py` is written, THE developer SHALL record in `term_audit.md`, for every listed value and by applying the Include and Exclude entries of `burden_test/inclusion_rules.md`: a disposition of exactly one of `include`, `exclude`, `questionable` or `not_disease` for the measureid of the Audit_Keyword; a reason code that passes Requirement 2 criterion 5 for each `exclude` and `questionable` disposition; and a note of 1 to 200 characters for each `not_disease` disposition (for example a value that names a lab test or a drug class rather than a condition). A value whose Normalized_Text appears in more than one table for the same measureid (for example "LDL Cholesterol" under both `cholesterol` and `LDL`) SHALL have the same disposition and reason code in every such table. Writing `rules.py` SHALL NOT wait for the bio teammate's review of the dispositions (Open Item 13).
8. THE Rules_Config term lists SHALL be built from the Term_Audit dispositions together with `burden_test/inclusion_rules.md`, so that for the measureid of each value's Audit_Keyword: every value with disposition `include` has an Include_Term with the same Normalized_Text; every value with disposition `exclude` has an Exclude_Term with the same Normalized_Text and the recorded reason code; every value with disposition `questionable` has a Questionable_Term with the same Normalized_Text and the recorded reason code; and no value with disposition `not_disease` appears as an Include_Term, Exclude_Term or Questionable_Term. Values that share one Normalized_Text across columns (for example "Asthma" in `meshTerms` and "asthma" in `conditions`) SHALL form one Rules_Config entry, per Open Item 14 and Requirement 2 criterion 6.
9. IF a listed value cannot be classified unambiguously as `include`, `exclude` or `not_disease` from the Include and Exclude entries of `burden_test/inclusion_rules.md` (for example "Diabetic Retinopathy" when diabetes is not separately listed, or "Lipoprotein(a)" in `ancestorTerms`), THEN the disposition SHALL be `questionable` with a reason code that passes Requirement 2 criterion 5, and THE Rules_Config SHALL list that value as a Questionable_Term of the Audit_Keyword's measureid with the recorded reason code, until a later edit of `rules.py` after the bio teammate's review moves it (Open Item 13).
10. THE Term_Audit SHALL run as a one-off development step before `pipeline/mapping/rules.py` is written, and THE Mapping_Pipeline SHALL neither run the Term_Audit nor read or write `term_audit.md` during `python -m pipeline.mapping`.
11. THE Term_Audit SHALL read only `pipeline/processed/studies.csv` (and `term_audit.md` for the check in criterion 13), send no network request, write no file other than `term_audit.md`, and write `term_audit.md` atomically per Requirement 9 criterion 11.
12. IF `studies.csv` is missing, cannot be opened, is not valid UTF-8, has a header row that differs from the 18-column list under "Input facts", or has a `meshTerms`, `ancestorTerms` or `conditions` cell that is not a JSON array of strings, THEN THE Term_Audit SHALL write an error naming the file, the failed check and (for cell errors) the line number and column, with no cell content, to stderr, exit with a non-zero code, and leave any existing `term_audit.md` byte-for-byte unchanged.
13. IF `term_audit.md` already exists and at least one disposition or reason/note cell in it contains a character other than whitespace, THEN THE Term_Audit SHALL leave the file byte-for-byte unchanged, write to stderr a notice naming the file and the number of filled disposition cells, and exit with a non-zero code, so that a rerun cannot erase recorded dispositions.
